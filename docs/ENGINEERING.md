# Kismet (formerly Agent Dates)

Your agent dates. You just say yes.

Dating and friends for Edge City India residents, and only for them (Mandrem, Goa, Oct 11 - Nov 1 2026; an independent app made for residents, not an official Edge City product): each resident gets a private agent that talks only to them, the server sends it on short dates with other residents' agents, and each human only answers yes or no to their own agent's recommendations (secret double opt-in). When both agents and both humans say yes, it's a match and they see each other's Telegram handle.

## Edge City only (2026-10-28)

Kismet is for Edge City India residents only (`src/lib/edge-city.ts`). Membership is self-attested, no verification gate: `users.edge_city` true = member, false = said no, null = not asked yet; `edge_weeks` (week1-3, optional, informational) and `edge_answered_at`.

- Asked once at sign-up everywhere: the web chat and WhatsApp ask "Are you at Edge City India?" right after consent and before any other question (read without the model; a no gets the waitlist and creates nothing); the `/join` quiz and the native app quiz (agent-dates-mobile branch `kismet-edge-only`) have it as their first step; `POST /api/signup` takes `"edgeCity": true` and `"edgeWeeks"` (`false` -> 403 `edge_city_only` with the waitlist; left out by a store app (client `ios`, `imessage` or `android`, from `X-Kismet-Client` or the body's `client`: App Store build 2 and App Review never ask and have nowhere to answer) or by a real demo sign-up (the demo key) -> a member, with `edge_answered_at` null (`edge-city.ts signupEdgeCity`); left out by an agent or the website -> the account is made out of the pool, the reply carries the question, and its "no dates" reason links `/home`). Agent Village sign-ups (and any village call for a resident) are members by definition.
- The pool: only members are dated (`db.ts poolOthers`, `engine.ts reserveDates`, the daily job), recommended (`views.ts meView` / `pendingRecommendations`, so the web chat, WhatsApp pushes, apps and summaries), dropped (`drop-store.ts`), shown on the Village Board and counted in its stats; photos through a recommendation only between members; `decideDate` accepts no new answer (so no new match) unless both are members. Matches made before stay (contacts were already swapped), and blocking, reporting, unmatching and deleting always work.
- Accounts from before: the migration marks Agent Village accounts, the App Review demo accounts (`users.is_demo`) and store-app sign-ups as members; everyone else is null and is asked once on their next visit: the web chat posts the question when it opens (once per 30 days), WhatsApp asks on their next message (commands still work), `/home` shows a Yes / No card, apps and agents see `edgeCity: {member, answered, weeks, question}` in `GET /api/me` and a summary line, and answer with `POST /api/me/edge-city {"edgeCity": true|false, "weeks"?: [...]}` (`GET` for the state). ## Website = a chat with your agent (sign in with Google or email)

The website is one conversation with Kismet at `/chat` (signed-out visitors get the landing page and `/sign-in`). It is the Kismet-by-text state machine (`src/lib/text/agent.ts`) on a `web` channel: the same consent, one-question-at-a-time interview, recap and YES sign-up, recommendations as cards with Yes / No (secret double opt-in unchanged), match cards, commands and free chat. The quiz at `/join` and the dashboard at `/home` still work.

- Sign-in: Neon Auth (Managed Better Auth on the Neon branch; `NEON_AUTH_BASE_URL` from the integration plus `NEON_AUTH_COOKIE_SECRET`, 32+ characters, in every Vercel environment). `src/lib/identity.ts` (server), `src/lib/auth-client.ts` (browser), `/api/auth/[...path]` (proxy), `src/proxy.ts` (only `/auth/done`: swaps Google's session verifier for cookies). Google uses Neon's shared OAuth app until our own client is added (that shared app is what shows "neon.tech" on Google's page and returns `{"message":"State integrity check failed"}` on a Neon host when a sign-in was started twice or its cookie was lost: steps in an internal runbook, not in this repo); codes come from Neon's shared mailer (`auth@mail.myneon.app`, rate-limited).
- The sign-in sheet (`src/components/sign-in.tsx`, helpers in `src/lib/sign-in-help.ts`): a bottom sheet on phones, a card on desktop; Google (one flow at a time, reset when the page comes back from Google), the 6-digit code in six boxes (paste and iOS autofill fill them all, a full code signs in by itself), or a private link. In a known in-app browser (Instagram, Facebook, Messenger, Threads, TikTok, LinkedIn, Snapchat, WeChat, LINE, Pinterest; Google refuses those with `disallowed_useragent`) the email code comes first, with how to open the page in a real browser; an unnamed webview gets a softer note. A failed Google return (`/sign-in?error=google&error=<code>`) is explained on the sheet. The Neon Auth client rejects on non-2xx answers instead of returning `{ error }`, so every call goes through `attempt()`.
- Chat-shell pages (`/`, `/chat`, `/sign-in`, `/chat/<id>`) paint `html`/`body` and the toolbar tint (`theme-color`) in the shell colour `#121013` with `color-scheme: dark` (`src/lib/theme.ts`), so no cream shows below the shell, in overscroll or behind iOS toolbars; the plain pages follow the system light / dark theme as before.
- A sign-in is only an identity. `auth_identities` joins it to a Kismet account once the chat sign-up finishes, or when the person presses Connect for a private-link account open in the same browser (`POST /api/chat/connect`, same-origin only; never automatic, so a planted private link can't capture someone's Google sign-in). `currentUser()` tries Bearer, then a joined identity, then the private-link cookie, so `/home`, `/edit` and `/api/me/*` work for Google / email users too. Sessions are checked against Neon Auth directly (no cookie writes in pages), cached a minute per instance; an identity without an account must still exist in `neon_auth."user"`. Deleting the account deletes its `neon_auth."user"` rows as well; a sign-in that never got an account is deleted by DELETE ME in the chat.
- Leaked private link: joined sign-ins have seniority. `GET/DELETE /api/me/sign-ins` and the link reset (`POST /api/me/token/rotate`, 5 a day per credential) remove only sign-ins joined after the requester's own; a removed sign-in is recorded in `revoked_identities` and can never join that account again, and every private-link browser session ends. Known limits: Neon Auth's own limiter keys on our server IP; legacy link cookies are accepted until 2026-11-20; on a link-only account the first sign-in to press Connect is the senior one. Rate-limit keys use `src/lib/net.ts` (IPv4 per address, also IPv4-mapped IPv6; IPv6 per /64; canonical email per inbox).
- Threads: `user_phones` with channel `web` and key `web:u:<user id>` (an account) or `web:a:<auth user id>` (signed in, still in the interview). The web adapter (`src/lib/text/web.ts`, `live: true`) sends nothing: the transcript is the chat, and `src/lib/text/web-chat.ts` renders its placeholders (`[recommendation date:<id>]`, `[match notice date:<id>]`, ...) for the owner only, re-checked on every read. Live means no quiet hours, no daily push cap, no STOP opt-out and a Telegram-only contact question. `GET /api/chat` (polled every 6 s, one request at a time) also flushes notices and pushes the next recommendation under a non-waiting lease; `POST /api/chat {"text", "buttonId"?}` sends one message. Limits are per person (sync 40/min, messages 20/min) with loose per-network ceilings, since a venue shares one Wi-Fi exit; new accounts are capped at 20 per network per hour on the YES that creates them. Names show only for an open recommendation or an open match; answered recommendations and closed matches render without one, and model text shaped like a placeholder is stored quoted.
- Neon console (Settings, Auth), needed for production: trusted domains `https://kismet-village.vercel.app` and `https://agent-dates.vercel.app` (Google's return redirect; email codes work without them), application name `Kismet` (the code email says the project name until then), our own Google OAuth client (redirect URI `{NEON_AUTH_BASE_URL}/callback/google`; checklist in an internal runbook, not in this repo) and SMTP sender.

## The interface: a chat app, open to everyone

Every other page lives in the `(site)` route group with the plain header and footer (`src/components/site-chrome.tsx`).
- Signed out, sending opens the sign-in popup; the words wait in this tab for 30 minutes and come back into the message box after sign-in (and consent), never sent on their own. The "+" popup offers: say it, type it, copy a prompt for your own AI (`/llms.txt`), WhatsApp.
- Edge City India residents only (see "Edge City only" above); Edge City India is also an app in the sidebar. Your agent takes part in at most 3 dates a day in all (`DATES_PER_DAY`, counted on both sides and re-checked in the insert), so at most 3 new people a day; `/api/me` reports `datesPerDay`.

## Every agent in its own box (Daytona)

With `AGENT_BOXES=daytona` and `DAYTONA_API_KEY` (optional `DAYTONA_API_URL`), each person's agent runs in its own Daytona sandbox, `kismet-<user id>` (`src/lib/agent-box/`), after Agent Village's one-agent-per-resident model. A date is written turn by turn: each box builds only its own agent's prompt (`box-program.ts`, uploaded as `kismet/agent.mjs`) from its own card, its memory and the lines the other agent said; Kismet calls the model and hands the line back; each verdict is decided in its own box. So no model call ever sees both people's cards (the one-call writer, still the fallback, does).

Security: boxes have all network blocked (`networkBlockAll`) and hold no secrets (Kismet's keys never enter a box); they hold the agent card (no contact, status, gender or orientation) and a memory of past dates (topic tags and scores, never names, last 30 lines). Nothing a box returns is trusted: prompt sizes are capped, lines are stripped of contact details and must not assume a gender (else the next model is tried), verdicts are schema-checked and normalised by `assembleDate`, the same checks as the one-call writer. Boxes stop after 3 idle minutes (idle time is what Daytona bills), archive after 3 days, and are deleted with the account. Any box failure falls back to one call. About 25 s per date (6 turns + 2 verdicts).

## Signals (from Index Network)

What someone wants right now, in their own words (`signals` table, `src/lib/signals.ts`): the chat model proposes a signal only when the latest message states a want, and it is saved only if every word appears in that message in order (`isOwnWords`: cut, never added or reworded). Up to 5 active; SIGNALS / PAUSE SIGNAL n / RESUME SIGNAL n / DROP SIGNAL n, or the sidebar buttons (`POST /api/chat/signals`). Active signals go into the embedding and the persona card ("Looking for right now"), so a new one changes who the agent dates. Private like notes; the activity log keeps only the signal id. The post-match check-in uses Index's outcomes: met, not useful, missed.

## Apps (iOS, iMessage, Android)

Auth: `Authorization: Bearer <token>` (the token from `POST /api/signup`, the same one in the private link `/u/<token>`). Also send `X-Kismet-Client: <channel>/<version>`, e.g. `ios/1.0.0`, `imessage/1.0.0`, `android/1.0.0`: it is recorded as the sign-up source and last seen per channel. Photo URLs need the same Authorization header.

`PATCH /api/me` (profile edit, the apps and `/edit`): the whole profile, as at sign-up. Only `telegram`, `availability`, `area`, `edgeCity` and `edgeWeeks` may be left out (unchanged); any other field left out is reset to its default (an empty bio, `relStatus` undisclosed, ...). An empty `telegram` (`""` or `null`) is accepted only when matches reach the account another way: its WhatsApp number (a Kismet-by-text account; this clears the Telegram) or, with no Telegram today, a message in Kismet. An account reached on Telegram gets 400 `telegram: ...`. Adding a Telegram through `PATCH` never changes `contact_method`, so a WhatsApp account stays on WhatsApp (the chat's `EDIT telegram <username>` does switch it to Telegram); an account with neither is then reached on Telegram, and can change it but not clear it. `GET /api/me?full=1` has `contact: {"kind": "telegram" | "phone" | "app"}` (how matches reach them).

`GET /api/me/recommendations` (iMessage extension): pending recommendations awaiting the user's yes/no, newest first, at most 20.

```json
{"recommendations": [{"dateId": "f4c9...", "matchId": "f4c9...", "name": "Priya", "why": "Fellow AI music builder who surfs at dawn.",
  "meetup": "Chess and chai at The Circle", "photoUrl": "https://kismet-village.vercel.app/api/photos/<id>" , "sharedInterests": ["AI", "Music"],
  "worldVerified": false, "createdAt": "2026-10-18T18:05:21.852Z"}], "count": 1}
```

Answer with `POST /api/me/decide {"dateId": "<dateId>", "decision": "meet" | "pass"}` -> `{"ok", "decision", "match", "matchWith"?, "plan"?, "text"}`. `matchId` is the same id; it becomes the match (and chat) id if both say yes. `plan` (text) is the confirmed date plan of a weekly drop, only on a match. Items in `/api/me/recommendations` also carry `"weeklyDrop": true|false` and `"plan": null | {...}` (below).

`GET /api/me/drop` ("This week's Kismet", see Weekly drop below): the latest drop (last 8 days) and when the next one comes.

```json
{"weeklyDrop": true, "schedule": "Wednesdays at 7 pm India time", "nextDropAt": "2026-10-28T13:30:00.000Z",
 "drop": {"dropAt": "2026-10-21T13:30:00.000Z", "status": "open", "dateId": "f4c9...", "matchId": "f4c9...", "name": "Priya", "why": "Fellow AI music builder who surfs at dawn.",
   "meetup": "...", "photoUrl": null, "sharedInterests": ["AI"], "worldVerified": false, "createdAt": "...", "weeklyDrop": true,
   "plan": {"text": "Sat 24 Oct, 5:30 pm: a sunset walk on Mandrem Beach", "why": "You both love AI and surfing.", "day": "Sat 24 Oct", "time": "5:30 pm",
     "at": "2026-10-24T12:00:00.000Z", "place": "Mandrem Beach", "activity": "a sunset walk on Mandrem Beach", "confirmed": false}}}
```

`drop` is `null` (no drop yet, or weekly mode off: `{"weeklyDrop": false, "drop": null}`), or `{"dropAt", "status": "open", ...}` (above: answer it with `/api/me/decide`), `{"dropAt", "status": "matched", "dateId", "matchId", "name", "plan"}` (both said yes; `plan.confirmed` true), `{"dropAt", "status": "answered"}` (nothing about the other side) or `{"dropAt", "status": "none"}` (no good match that time). `weeklyDrop` turns false (and `nextDropAt` null) once the event's last drop has gone out; the last drop still shows here.

`/api/me/notes` ("what your agent knows about me", private): `GET` -> `{"notes": [{"id", "text", "source", "createdAt"}], "text"}`; `POST {"notes": ["<fact>"]}` or `{"text": "<fact>"}` (1-280 chars, 10 per call, newest 50 kept) -> 201 `{"ok", "added", "notes", "text"}`; `DELETE {"noteId"}` or `{"all": true}` -> `{"ok", "deleted", "notes", "text"}`. `POST /api/signup` also takes an optional `"notes": [...]`.

## Records (db/schema.sql "Kismet records")

`users.signup_channel/signup_client`, `consents` (18+ and Terms version), `profile_history` (old/new value per changed field), `user_channels` (first/last seen per channel), `activity_log` (append-only, ids only, never message bodies), `agent_notes`, `dates.shown_a_at/shown_b_at` and `dates.model`. ## What deleting an account erases (and the reports it keeps)

`DELETE /api/me` (and DELETE ME by text, the village/MCP `delete`, "Delete my account") erases the profile and its history, dates, matches, messages, photos (blob files too), the sign-in (`neon_auth."user"`), agent notes, consents, channels, activity log, blocks made, World ID link, text threads, per-user rate-limit rows and a waitlist entry with one of its sign-in emails. What stays: reports they made (`reporter_id` null), salted counters, one anonymous `delete` activity row, and the reports others made about them (Deon, 2026-10-28: "Keep reports + update policy"):

- `reports.reported_id` is `ON DELETE SET NULL` (was CASCADE). `src/lib/report-history.ts`: each report carries `reported_keys`, HMAC-SHA256 (`SAFETY_HASH_KEY`) of the reported person's normalized Telegram (Telegram's format, 5+ characters; never a placeholder like `none`, `xxxxx`, `no_tg` or `12345`), phones (E.164-looking: contact phone and linked WhatsApp numbers), sign-in emails (lowercase, no +tag, Gmail dots ignored) and Agent Village resident key, never the contacts. Telegram is unverified, so a typed handle must not poison anyone: a report, a ban (`refreshReportKeys`, which also records a ban with no report as a reporter-less `actioned` report; unban deletes it), the daily backfill and the deletion carry the current Telegram only while the account is not hidden or banned; a contact change adds only verified ones (number, email, resident key). On deletion (`keepReportsOf`, in `deleteUser`'s transaction) the kept reports also get `reported_gone_at`, `reported_banned` / `reported_hidden` (hidden by its own counted reports, not by a pending match; so the history still counts after reporters delete their own accounts), notes without contact details, the name, Telegram or X handle, and no photo; dismissed reports go unless they were banned; a ban with no report is kept as a report with no reporter.
- Re-sign-up check (`checkReportHistory`), on every door: `insertUser` (web, apps, `/api/signup`, WhatsApp/web chat with the thread's number or sign-in email, Agent Village and MCP), `updateProfile` when the Telegram changes, a new contact phone or linked number, a new sign-in email (`linkIdentity`). If a verified hash (number, email, resident key; never the Telegram alone) matches reports about another account (a deleted one included) that was banned, deleted while hidden, or reached `AUTO_HIDE_REPORTERS` counted reporters (same rule as a report: day-old or verified reporters, same side of the demo line), the new account is hidden pending review and logged as `report_history`. Prior reports also count toward the auto-hide of later reports (`reportDate` -> `hideOnHistory`). Demo accounts get no hashes. `/admin` lists "Hidden by an earlier account's reports" (with that history; Restore sets `users.history_reviewed_at`, so those earlier reports stop counting) and "Kept reports, account deleted".
- Retention: the daily cron (`/api/text/cron`, `purgeKeptReports`) deletes kept reports 12 months after the deletion (`KEPT_REPORT_MONTHS`), and those with no `reported_gone_at` (deleted by code that does not stamp it: a build from before, a rollback, an old Preview) 12 months after they were filed, never sooner. The same step backfills hashes for reports filed before they existed (`backfillReportKeys`, 200 accounts a day).
- Telegram usernames are unverified, so a Telegram-only match never hides anyone (QA2 N-M2: an impersonator could get the real owner hidden): it is logged as `report_history_telegram` and listed in `/admin` ("Telegram matches an earlier account's reports") with the history. Only a WhatsApp number, sign-in email or resident key match hides (pending review). A new handle evades it either way.
- Failed deletions outside the database are retried (QA3): a photo file (Vercel Blob), the sign-in (`neon_auth."user"`) or the agent box (Daytona) that fails to delete is queued in `deletion_jobs` (`src/lib/deletion-jobs.ts`; kind + target: a blob pathname, a Neon Auth user id or the deleted account's id, never a name or contact). The daily cron retries due jobs as its last step, for at most 30 s (per kind 100 a run, 10 agent boxes, only kinds that can run now, so no backlog starves another; files and sign-ins together, then one by one; boxes one by one; a call with no answer in 15 s is a failed try; Daytona calls time out after 60 s; a job the budget cut off before its own try is not charged). Each try is counted before it runs, with backoff 1 h, 2 h, 4 h ... 7 days, so a run cut off mid-way still backs off; after 14 failures a job stops (`next_at = 'infinity'`) and keeps its `last_error` for a person (`select * from deletion_jobs where next_at = 'infinity'`). A Daytona 404/410 or a box already destroying counts as deleted; without `DAYTONA_API_KEY` box jobs wait. A queued sign-in that is linked to an account again (the person signed up again with Google before the retry) is kept and its job is done. Known gap: a person who signs in again and is still in the sign-up interview (no `auth_identities` row yet) when the retry runs loses that sign-in and signs in once more.
- The waitlist entry whose email is one of the account's sign-in emails (verified by Google or the emailed code) is deleted in the same transaction, with its `waitlist_join` log row, as its removal link does.
- Migration: `deletion_jobs` is new (`create table if not exists`, idempotent); `npm run db:migrate` before deploying (the build's schema check asks for `deletion_jobs.next_at`).
- `SAFETY_HASH_KEY`: 32+ random characters, the SAME value in Production, Preview and Development (they share one database; a different key matches nothing). Missing or short: nothing is hashed and nothing is checked (logged once; sign-ups and reports work as before), never a default key. Rotating it orphans every stored hash.

## Agent Village mini-app

- `/mcp` is the public read-only MCP server the Agent Village bridge calls (initialize, notifications/initialized, tools/call; stateless, no identity). Like `/api/public/*` it allows 60 calls a minute per network (`PUBLIC_PER_MINUTE`, then 429 / JSON-RPC -32000), except for calls with a valid `Authorization: Bearer $VILLAGE_PARTNER_KEY`, which come from Agent Village's one app server and keep the per-resident limits of the partner ops. Tool schemas in `src/lib/mcp.ts` are pinned byte-for-byte in the Agent Village manifest (`mini-apps/agent-dates/manifest.json` in Edge-City/agentvillage); change both together.
- `/api/village/{signup,summary,go,decide,delete,verify-link,notes}` is the server-to-server partner API for the Agent Village app server: `Authorization: Bearer $VILLAGE_PARTNER_KEY` (Production env only) plus the paired resident's opaque `residentId`, stored only as a hash in `users.village_resident`. Contract: `mini-apps/agent-dates/README.md` in the Agent Village bundle. Additive since then: `signup` takes an optional `"notes": ["<fact>"]`, and `notes` takes `{"residentId"}` (list), plus one of `"add": ["<fact>"]`, `"deleteId": "<note id>"` or `"deleteAll": true` -> `{"ok": true, "notes": [...], "text"}` (404 `note_not_found` for an unknown deleteId).
- The resident can also be named by the `X-Village-Subject: <opaque id>` header (Agent Village's subject header) instead of `residentId` in the body: same rule (1-128 of `A-Za-z0-9._:@-`), same hash, so the same account either way. Both given and different: 400 `subject_mismatch`. With the header, a body-less op may send an empty body.
- The same ops are authenticated MCP tools on `/mcp` (Agent Village app-token auth: their `MINI_APP_KISMET_KEY` is our `VILLAGE_PARTNER_KEY`). With `Authorization: Bearer $VILLAGE_PARTNER_KEY` and a valid `X-Village-Subject`, `tools/list` adds `kismet_signup` `{answers, telegram?, notes?}`, `kismet_summary` `{}`, `kismet_go` `{targetId?}`, `kismet_decide` `{dateId, decision}`, `kismet_notes` `{add? | deleteId? | deleteAll?}` and `kismet_delete` `{}` (schemas in `src/lib/mcp-partner.ts`). One implementation for both doors (`src/lib/village-ops.ts`): same checks, rate limits and texts. A result's first text block is the op's `text`, the second the JSON, and `structuredContent` the HTTP body; HTTP errors, a missing or wrong token or subject are `isError` with `structuredContent: {ok: false, error, message}`. Without the token and subject the server is the public one, byte for byte.

## World ID (optional badge)

Verified residents get a "✓ World ID verified" badge (shown to their matches and in recommendations) and a small ranking boost. Orb or Selfie Check, World ID 4.0 (`@worldcoin/idkit` 4.4.0). One World ID verifies one account (`world_ids`, `UNIQUE (nullifier, action)`; deleting the account frees it).

- Off unless `WORLD_APP_ID`, `WORLD_RP_ID` and `WORLD_SIGNING_KEY` are set (`WORLD_ACTION` defaults to `agent-dates-verify-2026`, `WORLD_ENV` to `production`). Off = no buttons, no links, `verification_unavailable`. Setup: `WORLD_ID_SETUP.md`.
- `/verify/<code>`: one-time link (one user, expires within 15 minutes, single use) that runs IDKit; `POST /api/world/sign` returns the RP signature, `POST /api/world/verify` checks the environment, forwards the result to `https://developer.world.org/api/v4/verify/{rp_id}` and stores the nullifier.
- Links reach residents through `/api/signup` (`verifyLink`), `GET /api/me` (`worldId.verifyLink`), the summary text, the home page card, and the partner op `verify-link`.

## Dates start on their own

Nobody has to ask: `autoStartDates` (lib/actions.ts) runs at sign-up (web, apps, Agent Village, WhatsApp) and when people show up (`GET /api/me`, `/api/me/summary`, `/api/me/recommendations`, the village `summary`), at most once per 30 minutes per person, and the daily job `GET /api/text/cron` (03:00 UTC = 08:30 IST; Vercel Hobby allows each cron at most once a day, `Authorization: Bearer $CRON_SECRET`; the weekly drop has its own cron, see Weekly drop) starts up to 3 dates for up to 40 residents with allowance left (120 dates per run, 6 at a time). The usual caps hold everywhere: 3 dates (so at most 3 new people) per resident per India day, 600 a day for the village. The same job flushes WhatsApp notices and pushes, and deletes sign-up conversations abandoned for 30 days.

## Weekly drop (after Ditto)

No swiping and no trickle: agents keep dating in the background, and once a week each resident gets ONE person with a complete date plan (when, where, what, and one line on why they fit). Code: `src/lib/drop.ts` (rules, pure and unit-tested), `src/lib/drop-store.ts` (Neon, model, push), venues in `src/lib/venues.ts`.

- Hold: while a drop is still to come, a date that finishes is `held`; it shows up nowhere (cards, counts, summaries, photos, decide, block/report) until it is released to that side (`dates.drop_a_at` / `drop_b_at`). Dates from before weekly mode, open recommendations and answers in flight keep working. Off switch: `KISMET_WEEKLY_DROP=off` (env), which also shows everything held. Per side: a held date someone was shown while nothing was held (`dates.shown_x_at`, set by `markShown`) stays visible to them when holding resumes, and only to them, so it never reveals the other agent's verdict.
- When: `DROP` in `src/lib/drop.ts`, Wednesday 19:00 `Asia/Kolkata` (weekday, hour, minute, time zone; no per-user time zones), plus `EXTRA_DROPS` (local times; today the event's last Friday, 2026-10-30 19:00). `EVENT_END` (2026-11-01, India time): no drop after it, and once the last drop before it has gone out (the end of its cron hour) nothing is held any more, so new recommendations show up at once for the event's last days (generic: no drop left before the end = no hold). Without an event end the weekly drop just goes on.
- Crons (Hobby: each job at most once a day, firing anywhere in its hour): `GET /api/text/drop` (`30 13 * * 3`) and `GET /api/text/drop-extra` (`30 13 * * 5`, acts only when an extra drop is due, otherwise answers "skipped"), and `GET /api/text/unheld` (`0 15 * * 5` = 20:30-21:29 India time: right after the last drop stops holding at 20:00, it pushes everyone with an active text or web chat thread so the dates un-held then go out on WhatsApp tonight, not at the next 08:30 push (web chat shows them on its next open anyway); `unheldPushDue`, otherwise "skipped"), all behind `CRON_SECRET`. A drop may go out up to an hour early (`DROP_EARLY_MS`, 18:30-19:29 India time). A drop stays due until the next drop's cutoff (the last one: until the event ends), so the daily job catches up anyone missed.
- Who: per person, the single best eligible date from a rolling pool (finished in the 28 days before the cutoff, `POOL_DAYS`), by `match.ts rank` (shared-interest similarity + their OWN agent's score). Eligible: their own agent said meet, not answered, not released to them yet, not closed, the other person visible (not banned or hidden, no block either way). Never the other side's verdict or answer, so a drop hints at nothing; a recommendation not picked one week (say B's drop went to C while A said yes to B) comes round in B's next drop. The first drop after shipping also draws on recommendations already showing but unanswered (that only adds a plan). No good match = nothing is sent. One query per person, without embeddings.
- Once: `drop_claims (user_id, drop_at)` is the claim: one drop per person per drop time, whatever the retries or double fires. A run that died after claiming is finished by the next one; a claim whose date went stale before it went out (answered, unmatched, blocked) is re-picked, and the release itself only takes an unanswered side.
- Run (`runDrop`): 1. claims; 2. one plan per claimed date for this drop, before anyone's release: a model call starts only if it would end (at its 20 s timeout) before the time kept for every push, otherwise the template; 3. release and push each person at once, 6 at a time, no new release after the budget (240 s weekly, 30 s in the daily catch-up). A person released but not pushed (a killed function, a failed send) has an ordinary open recommendation, which the daily job's push or their next web chat visit delivers.
- Plan: the time comes from both people's "free for a date" answer (`users.availability`: weekday_evenings, weekends, flexible; default flexible) after the drop; the venue (from `venues.ts`, Edge City list unless someone's `users.area` is plainly elsewhere) and the "why" line come from the model chain (`generateWithFallback`, json_schema, cancelled by an AbortSignal after 20 s), given only interests and the one-line bio, never status, openness, gender, orientation or names. Output is validated (known venue for that time, no private, romance or gender words, no contact details, no invented capitalized names, capped length) and falls back to a template plan. Where there is a choice, the time and the template venue rotate by the date id. Each side gets its own proposal, written for its own drop (`dates.plan_a` / `plan_b`; never reused from the other side's earlier drop, so a plan hints at nothing), shown with that person's drop (a time that has passed shows a week ahead). On a mutual yes the earlier proposal becomes the confirmed plan (`dates.plan`, `plan_confirmed_at`) in the same statement that makes the match, and both see it.
- Delivery: the web chat card and `/home` show "This week's Kismet" with the plan; WhatsApp gets "Your Kismet for this week: <name>. <why> Plan: <plan>. Up for it? Reply YES or NO." with Yes / No buttons, or, outside the 24 h window, the existing `kismet_new_recommendation` template with "Plan: <plan>. <why>" in its `{{2}}` parameter (plan first, so the 200-character limit never cuts it; no new template, and its fixed wording still says "your agent went on a date"). No "no drop this week" texts.
- Sign-up: one optional quiz step "When are you usually free for a date?" (plus where they are staying), also on `/edit`, `EDIT free <weekends|weekday evenings|flexible>` / `EDIT area <place>` by text, and `availability` / `area` in `POST /api/signup` and `PATCH /api/me` (left out = unchanged). The chat interview does not ask it (it stays as short as before).
- Shipping: run `npm run db:migrate` BEFORE deploying this code (it reads the new columns everywhere; the migration only adds columns and a table, so the code already live is unaffected). Set `KISMET_WEEKLY_DROP=off` for the Preview environment (`vercel env add KISMET_WEEKLY_DROP preview`): previews share the production database, and a preview must not hold dates or change what residents see.

## Content-Security-Policy (QA3)

- Pages: `src/proxy.ts` makes a fresh 128-bit nonce per request and sends `lib/csp.ts contentSecurityPolicy()` on the request (Next.js reads the nonce from it and puts it on its own scripts) and on the response. `script-src 'self' 'nonce-…' 'strict-dynamic'` (no inline scripts, no eval; dev adds `'unsafe-eval'`), `default-src 'self'`, `connect-src 'self'` (sign-in goes through `/api/auth`), `img-src 'self' data: blob:`, `font-src 'self'`, `style-src 'self' 'unsafe-inline'` (React style attributes and the World ID widget's `<style>`; a nonce can't cover attributes), `frame-src`/`object-src`/`base-uri`/`frame-ancestors 'none'`, `form-action 'self'`, `upgrade-insecure-requests` over https. `/verify/<code>` also allows World ID's font host and bridge.
- Trade-off: a nonce needs every page rendered per request, so the root layout awaits `connection()`. Pages that were static or ISR (`/`, `/privacy`, `/terms`, `/support`, `/board`, `/agents`, `/waitlist/remove`, 404) are now dynamic: no CDN-cached HTML, one function run per page view. `/board` keeps its two queries 30 s per instance, as its ISR did. Static files, icons and `/_next/*` stay cached.
- Not pages (`/api/*`, `/mcp`, `/llms*.txt`, icons, robots, sitemap, manifest: `NON_PAGE_SOURCES`): `next.config.ts` sends `NON_PAGE_CSP` (`default-src 'none'`) on those paths only, and the proxy sets no policy there (its matcher skips them; on `/api` and upper-case variants like `/MCP`, which Next's `headers()` also matches, `nonPagePath` returns early), so no response carries two policies. Photo URLs are absolute (`SITE/api/photos/<id>`), so on any other host (Preview, an alias) `img-src` also allows `SITE`.
- zod's eval probe (it builds faster parsers with `Function`) is switched off in the browser (`lib/zod-jitless.ts`, imported first by `lib/auth-client.ts`); otherwise every page with sign-in reported a violation.
- On Preview deployments Vercel's toolbar script has no nonce and is blocked (comments/feedback toolbar only).

## Kismet by text (WhatsApp)

Residents can text Kismet like a contact, no app: consent (18+ and terms) -> a short interview (the quiz fields, one question at a time, plus how matches reach them: Telegram, or this WhatsApp number only if they choose it) -> recap -> YES signs them up and sends their agent on dates. When a date produces a recommendation, Kismet texts it ("Your agent went on a date with Priya's agent. Why it clicked: ... Reply YES or NO") with Yes/No buttons: one open at a time, at most 4 a day, never 23:00-08:00 Asia/Kolkata. Outside WhatsApp's 24-hour window it sends the template `kismet_new_recommendation` instead; other notices wait for the person's next message. A mutual yes texts both people the agreed contact. Commands: HELP, MATCHES, PROFILE, EDIT <field> <value>, DATES, NOTES, FORGET EVERYTHING, PAUSE, RESUME, LINK [code], DELETE ME, STOP / START. Secret double opt-in and every privacy rule are unchanged (same actions as the web, apps and Agent Village).

- Code: `src/lib/text/` (`agent.ts` state machine with injected store/adapter/model/app, `parse.ts` commands, yes/no, quiet hours, interview order, `whatsapp.ts` Cloud API adapter, `memory.ts` test adapter, `model.ts` GMI prompts with strict JSON schemas, `store.ts` Neon, `runtime.ts` wiring). Another provider (an iMessage line) is a new `TextAdapter`.
- Routes: `GET/POST /api/text/whatsapp` (Meta verify handshake; `X-Hub-Signature-256` with the app secret; idempotent on the message id; one number's messages are serialized by a lease), `GET /api/text/cron` (the daily job, see below), `POST /api/me/link-code` (an 8-character code to text as `LINK XXXX-XXXX`; the app then approves it: `GET /api/me/link` lists requests, `POST /api/me/link {"approve": "<requestId>"}`), `POST /api/me/link {"code"}` (the reverse: text `LINK`, enter the code in the app, then reply YES on WhatsApp). Either way a code alone links nothing.
- Answers: buttons and plain YES/NO are final; anything fuzzy ("ok", "sure", a thumbs-up, the model's reading of a sentence) gets one "Just to confirm ... This is final" first. Consent and sign-up need the words YES or I AGREE. Match notices hold only the date id until delivered (re-checked then; dropped after an unmatch, block, report or deletion), wait out quiet hours, and outside the 24 h window go as the partner-free template `kismet_match_ready`. Transcripts store placeholders like `[recommendation date:<id>]`, never another resident's name, reason or contact.
- Tables: `user_phones` (thread per channel+phone: state, draft, opt-out, pause, last inbound for the 24 h window, pending recommendation), `conversation_messages` (transcript), `link_codes`; `users.contact_method` / `contact_phone`. All deleted with the account.
- Env: `WHATSAPP_ACCESS_TOKEN` (system user token), `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_APP_SECRET`, `WHATSAPP_VERIFY_TOKEN`, `WHATSAPP_API_VERSION` (v23.0), optional `WHATSAPP_TEMPLATE` / `WHATSAPP_TEMPLATE_LANG` / `WHATSAPP_TEST_PREFIX`, `KISMET_WHATSAPP_NUMBER` plus `KISMET_WHATSAPP_PUBLIC=1` (both needed for the public "Text Kismet on WhatsApp" buttons and links; set PUBLIC only once a production number anyone can text is live; the webhook works without it), `CRON_SECRET`. Today: the Meta test number +1 555 143 7970 (only verified recipients can receive).
